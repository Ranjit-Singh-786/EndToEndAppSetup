# SmartFarm: Step-by-Step Learning Guide

This guide is designed to help you understand the architecture, database configurations, and Docker integration patterns of the **SmartFarm** microservices system. Follow these steps sequentially to build a solid foundation.

---

## Step 1: Running the Application Without Docker (Locally)

To understand how each microservice functions, it is helpful to first run them directly on your host machine.

### A. Prerequisites
1. Install **Python 3.9+** on your system.
2. Ensure you have **MySQL** and **MongoDB** instances running locally. 
   *(Alternatively, run only the database containers using Docker, and execute your python code on the host).*

### B. Installing Dependencies
Create a virtual environment for each service and install its requirements. For example, in the `user-service` directory:
```bash
cd user-service
python -m venv venv
# On Windows:
venv\Scripts\activate
# On Unix:
source venv/bin/activate

pip install -r requirements.txt
```
*(Repeat the same process for `farm-service` and `monitoring-service` in separate terminal windows).*

### C. Launching Services
Run the services using `uvicorn`:
* **User Service (Terminal 1)**:
  ```bash
  cd user-service
  uvicorn app.main:app --host 127.0.0.1 --port 8001 --reload
  ```
* **Farm Service (Terminal 2)**:
  ```bash
  cd farm-service
  uvicorn app.main:app --host 127.0.0.1 --port 8002 --reload
  ```
* **Monitoring Service (Terminal 3)**:
  ```bash
  cd monitoring-service
  uvicorn app.main:app --host 127.0.0.1 --port 8003 --reload
  ```
* **Gateway Service (Terminal 4)** — serves the multi-page web UI:
  ```bash
  cd gateway-service
  pip install -r requirements.txt
  uvicorn app.main:app --host 127.0.0.1 --port 3000 --reload
  ```

Open your browser and navigate to the respective Swagger docs to verify:
* Web UI (Gateway): `http://127.0.0.1:3000`
* User Service Docs: `http://127.0.0.1:8001/docs`
* Farm Service Docs: `http://127.0.0.1:8002/docs`
* Monitoring Service Docs: `http://127.0.0.1:8003/docs`

## Step 2: Understanding FastAPI Microservice Structures

Every service in the project follows a clean, decoupled layout:
* **`main.py`**: The entrypoint. Configures middlewares (CORS, Request/Response Logging), initializes databases, registers endpoints, and hosts health status metrics.
* **`config.py`**: Loads environment configurations using Pydantic Settings. Grabs settings from the local `.env` file or container environment variables.
* **`database.py`**: Establishes database engines and connection pools.
* **`models.py` / `schemas.py`**: Separates database schemas (what is stored in the database) from Pydantic schemas (what the API accepts/returns). This separation is vital for building robust APIs.
* **`routers/`**: Grouped endpoints matching a specific logical domain (e.g. `farmers.py`, `crops.py`).
* **`services.py`**: Encloses the core business actions (CRUD database operations).

---

## Step 3: Understanding the MySQL Connections

The User and Farm services connect to separate MySQL databases (`smartfarm_users` and `smartfarm_farms`).
* **SQLAlchemy Engine**: Configured in `database.py` using `create_engine`.
* **PyMySQL**: Used as the database driver (`mysql+pymysql://`).
* **Connection Pools**: We enable `pool_pre_ping=True` to automatically recycle connection queries when they time out.
* **Automatic Init**: When the services start, the tables are automatically generated by the SQLAlchemy metadata script `Base.metadata.create_all()`.

---

## Step 4: Understanding the MongoDB Connections

The Monitoring Service uses MongoDB to handle flexible, document-based sensor telemetry readings.
* **PyMongo client**: Configured in `database.py`. It uses standard synchronous drivers which are simple and highly readable.
* **Database Init**: Connection validation occurs on startup (`app.on_event("startup")`) by calling `client.admin.command('ping')`.
* **Flexible Schemas**: Review how `additional_data` is saved as a nested document in `app/routers/monitoring.py`. If a sensor reports a new attribute, MongoDB swallows the data without requiring schema migrations!

---

## Step 5: Understanding the Gateway & Server-Rendered Pages

The web UI is not a static single-page app. The **Gateway Service** (`gateway-service/`) is a fourth FastAPI app that:

* Renders **Jinja2 templates** in `templates/` — one page per workflow (farmer registry, farmer form, farm workspace, crop form, monitoring panel, reading history, etc.).
* Calls the three domain services over HTTP exactly like they call each other — the browser never talks to ports 8001–8003 directly. Upstream URLs come from `app/config.py` (or environment variables).
* Uses **Post/Redirect/Get**: every form posts to the gateway, which calls the upstream service, then redirects the browser back with a success/error flash message. This is why pages work with JavaScript disabled.
* Enhances only the monitoring panel with **AJAX**: `static/app.js` fetches `GET /ajax/monitoring/{farm_id}` when the farm dropdown changes, and re-renders the metrics without a full page reload.

To see the boundary in action: register a farmer at `/farmers/new`. The gateway receives the form, posts to `user-service:8001`, and redirects to `/farmers` where the list page fetched its data from the same service over HTTP.

## Step 6: Creating Dockerfiles

Open the `Dockerfile` inside `user-service/Dockerfile`:
1. `FROM python:3.11-slim`: Pulls a lightweight base image with Python preinstalled.
2. `WORKDIR /app`: Defines the default executing directory.
3. `RUN apt-get update && apt-get install -y curl`: Installs `curl` so Docker can perform health checks inside the container.
4. `COPY requirements.txt .`: Copies requirements first. This layer is cached to speed up future builds.
5. `RUN pip install ...`: Installs all required packages.
6. `COPY . .`: Copies the service source code.
7. `EXPOSE 8001`: Informs Docker that the container listens on port 8001.
8. `CMD ["uvicorn", ...]`: Runs the server.

---

## Step 7: Building Docker Images Manually

Before using Docker Compose, you can build images individually. Run the following command in the `user-service` directory:
```bash
docker build -t smartfarm-user-service .
```
Verify the build is successful:
```bash
docker images
```
You will see `smartfarm-user-service` in the lists of available images.

## Step 8: Running Individual Containers

To run a built image as an isolated container:
```bash
docker run -d --name my-user-service -p 8001:8001 -e DATABASE_URL=mysql+pymysql://root:root@123@localhost:3306/smartfarm_users smartfarm-user-service
```
This command runs the container in detached mode (`-d`), mounts the host port `8001` to the container port, and injects configuration variables via environment flags (`-e`).

---

## Step 9: Understanding Docker Networking

When running microservices, containers must talk to each other (e.g. Farm Service calling User Service).
* If you run individual containers, they are placed in Docker's default bridge network, but they cannot resolve each other by container name.
* **Bridge Networks**: Docker Compose automatically defines a private bridge network (`smartfarm_net`). Within this network, containers resolve names using DNS. The Farm Service can call the User Service using `http://user-service:8001` instead of managing IP addresses.

---

## Step 10: Running the Entire System with Docker Compose

Docker Compose coordinates the startup, networks, and environment setups of all 6 containers using `docker-compose.yaml`.
* To start everything in the foreground (showing logs):
  ```bash
  docker compose up --build
  ```
* To start in the background (detached):
  ```bash
  docker compose up -d --build
  ```
* To tear down the sandbox:
  ```bash
  docker compose down
  ```

---

## Step 11: Understanding Volumes

If you restart a database container without mounting a volume, all user data disappears.
SmartFarm configures two named volumes:
```yaml
volumes:
  mysql_data:
  mongodb_data:
```
These tell Docker to mount storage from the host machine to `/var/lib/mysql` and `/data/db`. You can start, stop, rebuild, or destroy your containers; your farmer profiles and sensor history will remain intact.

---

## Step 12: Understanding Environment Variables

Database URLs and communication ports should never be hard-coded.
* The `.env` file in the root directory holds all variables.
* Docker Compose imports this `.env` automatically and passes variable values to the services (e.g. `${MYSQL_ROOT_PASSWORD}`).
* You can change the MySQL credentials in `.env`, run `docker compose up`, and the entire system updates to match the new settings.

---

## Step 13: Service-to-Service Communication Flow

Look at how the service boundaries are crossed during a request (e.g. creating a farm through the gateway):
1. Browser submits the farm form to the Gateway: `POST /farms` (plain HTML form).
2. Gateway forwards the payload to Farm Service: `POST http://farm-service:8002/farms`.
3. Farm Service pauses and executes a synchronous HTTP request via `httpx.get` to `http://user-service:8001/farmers/1` to verify the owner.
4. User Service returns `200 OK` with the farmer profile.
5. Farm Service creates the farm record in `smartfarm_farms` and returns `201 Created`.
6. Gateway redirects the browser to `/farms` with a success message.

The same pattern repeats for sensor readings: the Monitoring Service verifies the farm with the Farm Service before writing to MongoDB.

---

## Step 14: Enforcing Database Ownership

In SmartFarm, the MySQL container is shared, but database schemas are strictly separated:
* User Service connects *only* to `smartfarm_users`.
* Farm Service connects *only* to `smartfarm_farms`.
This structure teaches the fundamental microservice concept of **Data Isolation**. If you need to access farmer data inside the Farm Service, you are forced to go through the User Service's HTTP endpoints. This prevents database schema changes in one service from breaking other services.
